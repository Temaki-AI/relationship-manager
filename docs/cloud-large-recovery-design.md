# Large-Workspace Cloud Recovery Design

Status: bounded capture, manifest publication, independent reading, restore preparation, apply, rollback, cleanup, and queued background apply/rollback are implemented with an owner-only API and browser UI behind `CLOUD_LARGE_RECOVERY_ENABLED=false`. They are not enabled in the deployed product. The 16 MB interactive backup/restore limit remains enforced. Do not enable the new workflow or raise that limit without live quota and authenticated restore drills and a published-point retention policy.

## Implemented Capture Foundation

- Migrations `0015_boring_sharon_carter.sql` and `0016_brainy_rawhide_kid.sql` add tenant-scoped capture jobs, per-chunk metadata, lifecycle/revision guards, and one active job per workspace. No remote migration has been applied.
- Internal capture calls walk each CRM table in bounded keyset pages and store at most 3 MB of serialized rows per private, SHA-256-addressed R2 chunk. A D1 lease and revision fence prevent a changed workspace or stale attempt from publishing chunk metadata. A completed walk stops at `awaiting_verification`, which is intentionally not listed as a backup and cannot be restored.
- An internal discard call removes private objects in resumable pages. Workspace erasure waits for an active capture or verification lease and removes job records and private objects. A changed workspace invalidates an unfinished capture; its staged objects still require explicit discard or future stale-job cleanup.
- SQLite and workerd tests cover integer/text/composite cursors, more than 16 MB of staged data, tenant separation, concurrent starts, expired-lease retry, edit-during-upload, erasure, and bounded removal. These tests do not validate live Cloudflare quotas or a production restore.

## Implemented Private Manifest

- Migration `0017_nosy_sage.sql` adds resumable verification progress and a database guard for `manifest_ready`. It also makes `workspace_id` immutable on the captured CRM tables, closing a revision-fence gap from cross-workspace row moves. No remote migration has been applied.
- Each verification call re-reads one R2 chunk, checks its hash and metadata, validates its row schema, key order and tenant identity, and compares its rows with the unchanged D1 source. Every eight verified chunks are described in a bounded R2 manifest part. The final call checks source row counts, chunk counts, and relationships, writes a small root manifest with a hash chain over its parts, re-reads it, and publishes `manifest_ready` only behind the same revision fence.
- `manifest_ready` remains private and is not shown in standard backup listings or used to authorize workspace deletion. When the feature flag is enabled, the owner-only Advanced recovery page lists selectable private snapshots separately.

## Implemented Independent Read Pass

- Migration `0018_colorful_johnny_blaze.sql` adds a tenant-scoped read job with a durable cursor, row counts, part hash chain, and short lease. A read can start only from a private `manifest_ready` root; capture discard and workspace erasure wait for active read leases. No remote migration has been applied.
- The reader validates the root, current manifest part, and one chunk per step directly from R2. It checks identity, schema, sizes, checksums, key order, and row shape, then fences the cursor update in D1. On the last chunk it compares the part chain and per-table counts with the root. It can complete even if the capture job's D1 chunk-index rows are gone; a changed artifact invalidates the read job, while a transient R2 outage leaves it retryable.
- This is validation-only. A `verified` read job records what was checked at that time, not a permanent promise that R2 objects cannot later change. The private apply engine re-reads and verifies bytes as it writes them, preserves a pre-restore point, and validates the final destination graph before reopening normal access.

## Implemented Stale-Job Cleanup

- The existing 15-minute scheduled Worker now runs a bounded snapshot cleanup pass. It removes invalid captures in resumable 100-object R2 pages, invalidates unfinished jobs only after seven idle days and an expired lease, and removes stale validation read cursors after one day. R2 deletion failures retain the invalid job for a later retry; active leases are protected.
- Published `manifest_ready` objects are deliberately not pruned by this pass. Their future count/size retention policy must be coordinated with restore pins and rollback guarantees; deleting them solely because they are old could remove the only usable recovery point for a large workspace. This cleanup does not scan for arbitrary R2 keys outside known job prefixes.
- Idle `preparing`, `ready`, and `invalid` restore preparations expire after seven days; active apply/rollback states do not expire automatically. Completed and rolled-back restore records retain their referenced capture and read jobs for 30 days, then a bounded cleanup pass removes the terminal record before the normal read/artifact cleanup can reclaim it. Published manifests still require an explicit, product-level retention policy. Direct discard refuses captures referenced by any restore record, including terminal records; this matches database foreign keys.

## Restore Preparation (Internal)

- Migration 0019 stores one active preparation per workspace. Each bounded call verifies the chosen published manifest using the independent R2 reader, captures the current workspace as a new rollback point, publishes its manifest, and independently verifies that rollback point. No CRM row is replaced during preparation.
- A workspace revision fence covers every step and the final `ready` transition. Edits invalidate a preparation, including one previously marked ready. Active preparations pin their capture and read jobs against discard and scheduled cleanup; expired preparations release those pins. Erasure waits for active preparation leases.
- A `ready` preparation is not a restore. It does not guarantee R2 bytes will remain unchanged, cannot be selected in the UI, and does not permit destructive operations. The private apply engine described below rechecks bytes and keeps a durable maintenance lock; the product still needs authenticated controls and live-service validation.
- Migration 0020 adds delete guards to all CRM snapshot tables, closing the gap left by the existing insert/update guards. Cloud API dispatch now returns a maintenance response for ordinary requests when a workspace is not active; backup status stays readable, and erasure can be resumed. Erasure deletes its graph while active and commits the `erasing` lifecycle in the same D1 batch, with a second lifecycle check inside the batch to reject a concurrent restore.

## Private Apply and Rollback Engine (Internal)

- Migrations `0021_useful_stone_men.sql` and `0022_tough_boom_boom.sql` add durable apply cursors, a source selector, and terminal rollback state. They have not been applied remotely. A verified preparation can atomically enter `restoring`, blocking ordinary cloud API access and CRM writes. Deletion runs in reverse dependency order, at most 64 rows per step. Writing consumes at most four verified snapshot rows per D1 batch and rechecks R2 hashes, schema, identity, and manifest chains before advancing the cursor.
- A separate bounded date-repair pass restores contact timestamps altered by interaction triggers. Final verification compares every destination row with the source chunks, checks counts and graph references, neutralizes stale mutation receipts/import jobs, resets email consent and backup scheduling, then reopens the workspace. Any failed step leaves maintenance in force and can be retried.
- Rollback can switch an interrupted or corrupt target application to the independently verified pre-restore capture only after the current lease expires. It resets the cursor and uses the same bounded delete/write/verify protocol, ending in `rolled_back`. Tests exercise partial writes, failed verification, live-lease refusal, tenant isolation, and both SQLite and workerd D1/R2 behavior.
- `GET/POST /api/settings/large-recovery` and job-specific step/apply/rollback/pause/resume/cancel/delete actions are routed through the existing authenticated cloud workspace dispatch. Only the workspace owner can use them. A separate Settings page shows snapshot and restore phases, polls apply/rollback progress, and demands typed confirmation before preparation, application, rollback, or deletion. It can resume or roll back an already locked workspace even if the feature flag is later turned off. The local browser test uses mocked cloud responses; it is not a live authenticated Cloudflare restore drill.
- Migration `0023_married_zaran.sql` adds persisted background state and a progress version. Apply and rollback enqueue one Cloudflare Queue message; each consumer invocation advances one fenced step, increments the version, then enqueues the next message. Duplicate or stale messages are ignored. Owner pause/resume and rollback increment the version, invalidating old messages. After repeated failures the job becomes visibly failed and can be resumed or rolled back. The existing 15-minute Cron republishes running jobs that have not advanced for three minutes and have no live lease, covering a crash between a D1 commit and queue publication. Capture and preparation still advance from the page, but applying a snapshot no longer needs an open browser.
- Before deployment, create `everclose-large-recovery` and `everclose-large-recovery-failed` in the target Cloudflare account, apply migrations through 0023, and deploy the Worker with its Queue producer/consumer bindings. Provisioning, Queue costs and quotas, and a rollback path should be reviewed before this infrastructure change. Neither queue has been provisioned here; no remote migration or deployment occurred.
- Before release: settle published-point and pre-restore-point retention, including orphaned R2 objects; exercise large workspaces against live D1/R2/Queue limits and run an authenticated end-to-end restore drill including worker termination, message loss, and rollback. The interactive 16 MB guard remains unchanged.

## Safety Contract

- A completed backup must be a complete, verified graph from one workspace revision. In-progress chunks are private, unlisted, and unusable for restore or destructive-operation protection.
- Every destructive operation still needs a verified pre-operation recovery point. If a workspace cannot be captured safely, deletion and restore fail without changing CRM rows.
- Restore must preserve a verified pre-restore point, block ordinary reads and writes while replacement is incomplete, resume after interruption, and offer rollback. A partial graph must never be reported as restored or shown as normal CRM data.
- File integrity, tenant identity, schema version, row counts, references, and uniqueness must be checked before replacement. Completion must recheck the whole restored graph before reopening the workspace.

## Proposed Job Protocol

1. Capture tables in dependency order using bounded keyset pages. Store each page as a private R2 chunk with a hash, size, row count, table, and cursor. Persist the expected workspace revision and a lease/fencing token in D1. A changed revision invalidates the job and its chunks rather than publishing stale data.
2. Write a manifest only after every table is complete and every chunk is re-read and verified. Atomically mark the private manifest ready under the same revision/lease guard. The root, bounded parts, independent read pass, and stale-job cleanup now exist; published-point retention, download, and a general orphan scan still need to account for every object.
3. Before restore, verify the target manifest and capture a complete pre-restore backup with the same protocol. Enter a durable maintenance state that rejects normal CRM access. Apply small transactional batches in foreign-key order, saving the cursor after each batch; resume on retry and roll back from the pre-restore point if validation or application fails.
4. Verify final row counts, references, foreign keys, and workspace identity. Reset email consent and delivery baselines as the current restore does. Reopen the workspace only after validation and make incomplete/failed jobs visible with Resume or Roll back controls.

The current D1 triggers reject inserts and updates when a workspace is not active. A resumable restore therefore requires narrowly fenced maintenance writes inside each D1 transaction, not a broad trigger bypass. The existing one-request JSON snapshot and restore path should remain for small workspaces until the new path passes fault injection, cross-workspace, concurrency, interruption, and live quota tests. Cloudflare documents [D1 query and batch limits](https://developers.cloudflare.com/d1/platform/limits/), [transactional `batch()` behavior](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch), and [R2 multipart behavior](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/#r2multipartupload).
