# iPhone Calendar bridge

Implementation status: 4 October 2026. This is a local native implementation awaiting a supported native build and physical-device verification. It does not establish readiness for the personal beta or public release.

Open a plan from the native Agenda or a person's Plans screen and choose **Calendar**. The first review contains a title, location and either exclusive all-day dates or timed dates with a timezone. The title defaults to the plan's type; private CRM summaries and notes are not copied. Review the fields, then choose **Open system event editor**. Apple’s editor controls the destination calendar, visibility, guests and invitation effects. Saving an event never completes the plan or logs an interaction.

On iOS 17 and later, initial creation uses the system event editor without requesting broad Calendar read access. The installed Expo 57 legacy implementation requires Calendar permission on iOS 16; the app checks it before recording an editor attempt. The app does not request Calendar access at startup. **Verify original event**, searching a chosen calendar and editing an existing event each require explicit full read access. The config declares Calendar explanations and no Reminders permission. Android Calendar permissions are removed; the bridge is available only on iPhone/iPad. [Expo 57 Calendar reference](https://docs.expo.dev/versions/v57.0.0/sdk/calendar-legacy/).

Creation stores an account-scoped, immutable review and receipt before opening the editor. Its URL contains only the stable plan UUID and operation UUID. The native editor cannot accept a client-supplied event ID, so an attempted creation is never repeated automatically. A cancelled creation permits a new review. An unopened review can be discarded locally. A saved or unconfirmed creation retains its original receipt even when an acknowledgement is lost, the app restarts, the plan is removed or the workspace is restored. An observed ID is an alias, not permanent identity: EventKit can change it when an event moves.

Verification reads the original event and checks its exact receipt URL. If the ID is missing, choose one calendar and a bounded date window, search for that marker, inspect the unique result and explicitly accept it. The selected result is reread before acceptance. No match or several matches leave the receipt unresolved; the app does not create a replacement. Recurring events and detached occurrences require manual Calendar review. A removed/changed marker also pauses the bridge. These limits preserve uncertain results rather than guessing that an earlier save failed.

Reading defaults to off, separately from creation. **Keep this event's facts updated on this phone** retains only its ID, calendar ID, title, start/end, all-day state, timezone, receipt URL and recurrence/cancellation flags. A small local Expo module reads these fields directly from EventKit, using `TimeZone.identifier`; Expo's localized timezone abbreviation is not treated as an IANA identifier. A floating event uses the observing phone's current timezone. Event notes, guest lists and bodies are not copied. The native module is required in a development or distribution build; Expo Go and a JavaScript export cannot verify its behavior. [Local Expo modules](https://docs.expo.dev/modules/get-started/).

**Follow the event date for this plan** is another explicit choice and also enables reading. Accepting it can change the plan date immediately; later reads follow the event's civil start date. Only `planned_date` is changed, with an original-base patch in the existing plan outbox. Notes, summary, person identity, completion and interaction history remain intact. Receipt, plan and outbox writes commit together or roll back together. A manual or other-source date change makes following sticky-off even if the date is changed back before the next read. Completion, deletion, unavailable events, cancelled/recurring events, lost permission, a moved observed identity or a changed recovery epoch suspend updates and require fresh review. Editing the original in Apple's editor also suspends following until it is explicitly verified again.

Foreground synchronization checks at most 50 enabled receipts per pass, no more often than every 15 minutes per receipt; it never opens a permission prompt. Calendar freshness depends on this phone running. Operational receipts, consent and event facts stay in its account-isolated SQLite cache. Approved plan-date changes use cloud protocol 4 and reach web/other phones. The bridge does not yet publish Apple event facts or its receipt to the cloud, provide an arbitrary Apple Calendar event directory, or reconcile the same event seen through Google and EventKit. It refuses creation when the phone already knows a saved or queued Calendar association for that plan, but a stale/offline phone cannot reserve a plan against a concurrent web publication. Distributed reservation and cross-source identity review remain beta engineering gates.

The build-11 source candidate adds an online, shared reservation before new editor
attempts, minimal publication-status review and durable acknowledgements. Offline
drafting remains available; an unopened shared claim must be released before its
private draft is discarded. Schema 17 preserves schema-16 data and receipts.
This candidate and migration 49 are undeployed, so the paragraph above describes
the installed build-10 boundary. Legacy adoption, recovery/session reconciliation
and cross-source identity review still require implementation. See
[shared Calendar coordination](calendar-publication-coordination.md).

Native schema 14 adds `apple_calendar_receipts` and lifecycle/date guards; schema 13 upgrades preserve existing relationships, linked sources, queues, caches and cursors. Cloud D1 migration 44, CRM recovery schema 14 and sync protocol 4 are unchanged by this bridge. Receipts intentionally have no cascading plan foreign key, preserving evidence of an uncertain external effect after plan removal. Removing local account storage removes local receipts; account erasure must therefore explain which externally saved events remain in Calendar rather than claim to delete them.

Before calling this ready, build with the Expo 57 supported toolchain and verify on an installed iPhone: iOS 16 denial and iOS 17 creation without reads; save/cancel/delete and invitation effects; receipt URLs after iCloud/Google-backed calendar synchronization; moved IDs; lost replies and restart; limited/offline accounts; all-day exclusive ends in Lisbon, UTC and Los Angeles; DST gaps/folds and midnight dates; sticky manual corrections; account switching, recovery, larger text and VoiceOver. The available Xcode is 26.2; Expo 57 requires 26.4+. Syntax checking, autolinking resolution, SQLite/adapter tests and Hermes export provide narrower evidence and do not replace this gate. [Expo 57 requirements](https://docs.expo.dev/versions/v57.0.0/).
