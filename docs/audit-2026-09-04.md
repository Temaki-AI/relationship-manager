# Everclose CRM: Engineering and Product Audit

Date: 4 September 2026

## Assessment

Everclose has a useful personal relationship data model and a coherent visual foundation. The cloud product is not yet ready for a broad public launch: several visible features are placeholders, and some safety guarantees in the interface are not implemented by the cloud backend.

The highest-value next release should establish trust and make a small number of daily actions effortless. Adding more screens, integrations, or AI before fixing those foundations would increase the gap between what the product promises and what it delivers.

Recommended positioning: **Remember what matters. Follow through with the people you care about.** Use Everclose as the consumer-facing name; CRM can remain a category descriptor. The initial audience should be people maintaining friends, family, and a selected professional circle, rather than sales teams managing leads.

## Scope and Evidence

- Reviewed the current working tree, including uncommitted and untracked application files. This is a checkout audit, not proof that the live deployment matches it.
- Reviewed Google authentication, tenant scoping, cloud routing, contact CRUD, relationship history, reminders, calendar, imports, exports, backup and erasure flows, and CI coverage.
- Inspected the running local application using disposable demo data at desktop size and a 390 x 844 mobile viewport. Viewed the dashboard, contact directory, profile, calendar, and contact creation form.
- Restored dependencies with `npm ci`. All 196 existing tests, ESLint, and TypeScript checking passed.
- Executed the actual cloud handler source against the cloud SQL migrations using a disposable SQLite-backed D1 API adapter. This reproduced the findings listed below. It does not simulate every Cloudflare runtime behavior, OAuth, R2, or network failure.
- `npm audit --omit=dev` reported 14 affected packages: 8 high, 6 moderate, 0 critical. Some are build/deployment dependencies pulled into the production dependency graph; these counts are not evidence of 14 exploitable production vulnerabilities.
- Did not change application behavior, deploy, inspect private production contacts, or run the complete Playwright, native iOS, or production build suites. Visual observations are not a full accessibility certification or performance benchmark.

## Findings, Ordered by Impact

### 1. P1: Deletion promises recoverability that cloud mode does not provide

The contact and bulk-delete dialogs promise a verified recovery point. Success messages say that it was saved. Cloud deletion executes a direct SQL DELETE and creates no recovery point. The Settings restore action calls an endpoint that cloud middleware does not route and rejects with 501.

This can lead a user to delete information believing that they can restore it through the app.

Evidence: [delete handler](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/contact-api.ts:301>), [bulk deletion](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/contact-api.ts:173>), [UI promise](</Users/fernandoamaral/Dev/Personal CRM/app/contacts/page.tsx:646>), [profile promise](</Users/fernandoamaral/Dev/Personal CRM/app/contacts/[id]/page.tsx:978>), [restore action](</Users/fernandoamaral/Dev/Personal CRM/app/settings/page.tsx:253>), [cloud routing](</Users/fernandoamaral/Dev/Personal CRM/middleware.ts:104>).

Fix first: implement recoverable deletion and a tested, tenant-scoped restore path. Until then, remove the false recovery guarantees and disable unsupported restore controls. Database-level operator recovery is not equivalent to the promised per-user recovery workflow.

### 2. P1: Request retries can create duplicate records

Cloud create handlers ignore `Idempotency-Key` and always report `Idempotency-Replayed: false`. The UI retains the key after uncertain network failures and tells the user that retrying is safe.

Reproduction: submitting the same contact body twice with the same UUID key returned two different contact IDs. The same missing protection exists for interactions, plans, reminders, and children.

Evidence: [contact create](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/contact-api.ts:228>), [reminder create](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/core-api.ts:79>), [retry assurance](</Users/fernandoamaral/Dev/Personal CRM/app/contacts/[id]/page.tsx:648>).

Fix: a durable, workspace-scoped idempotency ledger, normalized request hash, and atomic write/replay behavior. Test lost responses and repeated requests against the cloud implementation.

### 3. P1: Conflict detection does not prevent simultaneous overwrites

Cloud contact updates read the current record, compare its revision, and then perform an unconditional UPDATE by ID. Two requests can both pass the revision comparison before either writes.

Reproduction: simultaneous edits carrying the same revision both returned 200; the second name replaced the first. The local implementation wraps this check and write in a transaction; the cloud implementation does not provide the equivalent guarantee.

Evidence: [cloud update](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/contact-api.ts:280>), [local comparison](</Users/fernandoamaral/Dev/Personal CRM/lib/contact-revision.ts:67>).

Fix: store a version and use an atomic conditional update such as `WHERE workspace_id = ? AND id = ? AND version = ?`, checking affected rows. Plan completion has a related race: it conditionally updates the plan but unconditionally inserts an interaction after a separate pre-read. Make completion and its derived interaction exactly-once.

### 4. P1: The cloud dashboard does not perform the product's core job

The cloud overview hard-codes overdue and strong-relationship counts to zero and returns empty focus and smart-list arrays. The smart-list endpoint always returns an empty list. Contact detail returns an empty timeline and a generic brief despite stored history.

Reproduction: an explicitly overdue contact still produced zero overdue relationships and an empty feed.

Evidence: [overview](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/core-api.ts:216>), [smart-list handler](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/core-api.ts:311>), [contact brief and timeline](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/contact-api.ts:265>).

Fix: port the real deterministic calculations into shared domain services with storage adapters. Do not present missing calculations as factual zeroes or an all-clear state. This is more important than adding AI recommendations.

### 5. P1: Birthday alerts and reminder completion are inconsistent in cloud mode

The cloud notification endpoint explicitly returns `birthdays: []`, so saving a birthday lead time does not result in a birthday notification. The normal reminder query includes completed reminders. The reminders UI removes a completed item and immediately reloads that query, bringing it back into the queue without filtering it out.

Reproduction: after completing a reminder, a normal list request returned it with `completed_at` populated. A contact with today's birthday produced no birthday notification candidate.

Evidence: [notification query](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/core-api.ts:64>), [reminder listing](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/core-api.ts:71>), [UI refresh](</Users/fernandoamaral/Dev/Personal CRM/app/reminders/page.tsx:118>).

Fix: default to open reminders, offer a distinct completed view, implement birthday occurrences and lead times, and use a single scheduling policy across dashboard, calendar, and delivery.

Browser notifications currently depend on an open app and page polling. There is no push-event handler or server scheduler in the checked configuration. Reliable closed-app delivery is a separate product requirement, not a styling change. See [notification provider](</Users/fernandoamaral/Dev/Personal CRM/components/reminder-notification-provider.tsx:115>) and [service worker](</Users/fernandoamaral/Dev/Personal CRM/public/sw.js:1>).

### 6. P1: Large imports exceed the cloud execution model

The cloud import advertises up to 5,000 contacts, but processes each using one duplicate query and one insert, sequentially in a single request. A 5,000-new-contact import needs approximately 10,000 queries, excluding authentication. That exceeds the published D1 per-invocation limits of 1,000 on Paid and 50 on Free. The current plan was not inspected. Per-row failures are caught and labeled invalid contacts, which can hide infrastructure failures as bad user data.

Evidence: [import loop](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/portable-api.ts:72>), [advertised cap](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/portable-api.ts:110>), [Cloudflare D1 limits](https://developers.cloudflare.com/d1/platform/limits/).

Fix: staged imports with preview, bounded chunks, a durable job ID, resumable progress, idempotent chunks, and a reconciliation report. Preserve the original file until the job is confirmed, then apply the stated retention policy. Do not report infrastructure failures as invalid rows.

### 7. P2: Cloud imports silently omit information

CSV normalization catches errors and drops rows without adding them to the skipped count. Reproduction: a two-row CSV with one malformed email reported one import, zero skipped, and no errors.

The cloud CSV field map also omits exported `custom_fields`, photo, and last-contacted fields. A contact export/import round trip therefore cannot preserve all exported context. Duplicate detection treats identical name plus missing birthday as a match, which can silently discard distinct people sharing a name.

Evidence: [CSV mapping](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/portable-api.ts:57>), [silent normalization skip](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/portable-api.ts:140>), [duplicate criterion](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/portable-api.ts:75>).

Fix: every row receives an explicit outcome; ambiguous name matches go to review; round-trip tests cover every supported field and format. Clearly distinguish contact export from full relationship-history backup.

### 8. P2: Contact filters and search do not match the interface

The UI sends a `tag` filter, but the cloud list handler does not read it. Search promises notes and imported context, while cloud SQL searches only name, nickname, email, and phone.

Reproduction: requesting `tag=friends` returned a contact tagged only `work`.

Evidence: [UI query](</Users/fernandoamaral/Dev/Personal CRM/app/contacts/page.tsx:113>), [search promise](</Users/fernandoamaral/Dev/Personal CRM/app/contacts/page.tsx:665>), [cloud list](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/contact-api.ts:94>).

Fix: share filter semantics and pagination contracts. Add tests for tags, notes, companies, locations, and empty results. Persist search and filter state in the URL so Back restores the user's context.

### 9. P2: Dates and interaction edits can distort relationship state

The calendar client sends the user's time zone, but the cloud calendar groups reminders by a substring of their stored UTC timestamp. Reproduction: `2026-09-04T23:30:00Z` was assigned September 4 for Europe/Lisbon, even though its local date is September 5.

Cloud interaction edits and deletions do not recalculate `last_contacted`. Deleting the most recent interaction left its date on the contact in the adapter reproduction.

Evidence: [calendar query](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/core-api.ts:226>), [interaction mutations](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/core-api.ts:92>).

Fix: distinguish date-only occasions from timestamped reminders; consistently apply workspace time zone and daylight-saving rules. Derive last-contacted from valid history plus an explicit manual baseline. Define one February 29 policy and reuse it everywhere.

### 10. P1: Cloud backup lifecycle and erasure are incomplete

Backups read multiple tables independently, so concurrent writes can yield a snapshot containing records from different moments. The API advertises retention of 20 but does not enforce it. Listing reads only the first 100 objects without following a cursor. Erasure deletes only one page of up to 1,000 objects and returns success even when further pages could remain.

Evidence: [backup listing](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/backup-api.ts:44>), [snapshot reads](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/backup-api.ts:92>), [erasure](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/backup-api.ts:115>).

Fix: consistent snapshots, complete pagination, enforced retention, restore drills, and resumable erasure with a verifiable completion state. Explicitly distinguish deleting CRM content from deleting the Google-linked account and its authentication records.

### 11. P2: Cloud mode exposes unsupported actions and weaker request safeguards

Cleanup, enrichment, LinkedIn import, and numeric group-membership routes are missing from the cloud rewrite allowlist. The UI and shared capabilities still expose some of these actions. The local streaming request-size guards are also bypassed by direct `request.json()` / `request.formData()` calls in cloud handlers; the file limit is checked after multipart parsing.

Evidence: [cloud route allowlist](</Users/fernandoamaral/Dev/Personal CRM/middleware.ts:104>), [capabilities](</Users/fernandoamaral/Dev/Personal CRM/lib/data-capabilities.ts:10>), [enrichment action](</Users/fernandoamaral/Dev/Personal CRM/app/contacts/new/page.tsx:43>), [multipart parsing](</Users/fernandoamaral/Dev/Personal CRM/lib/cloud/portable-api.ts:102>).

Fix: explicit capability responses per backend; unsupported controls hidden or clearly unavailable; centralized pre-parse size limits and workspace quotas. Add a route-contract suite that exercises every visible action in cloud mode.

### 12. P2: Dependency advisories now fail the project's stated CI policy

The locked Next.js installation is 15.5.20. npm reports affected Next.js ranges and other advisories in the installed graph. CI runs `npm audit --audit-level=moderate`, so the current advisory results require resolution or documented, justified handling.

Evidence: [dependency configuration](</Users/fernandoamaral/Dev/Personal CRM/package.json:36>), [CI policy](</Users/fernandoamaral/Dev/Personal CRM/.github/workflows/ci.yml:28>).

Fix: triage reachability, update compatible patched releases, validate OpenNext compatibility, and rerun cloud build and journeys. Do not apply `npm audit fix --force` indiscriminately: suggested fixes include incompatible dependency changes. No exploitability claim is made from the scanner output alone.

## UI and Experience Recommendations

### Make Today the product's center

The current dashboard prominently features data connections, ownership links, counters, and duplicated smart-list previews. Those are useful supporting functions but compete with the reason to open the app.

Replace the default view with three to five specific opportunities: who, why now, the relevant context, and an immediate action. Each card should offer Reach out, Log contact, Snooze, and Dismiss. Show an occasion and a cadence reminder for one person together rather than as separate chores. Move setup and transfer prompts out of the daily experience after onboarding.

Example: "Ana's birthday is next week. You last spoke about her move. Send a message / Plan something / Remind me Friday." Do not automatically claim that opening a messaging app means an interaction occurred.

### Put people above management controls

At 390 x 844, the first directory contact begins around 660 pixels down. The permanent bulk-action card defaults to Delete contacts and occupies much of the useful screen.

Use a compact title, visible search, one Filters button, and a dense person list. Show bulk controls only after entering selection mode. Move import/export/cleanup to a secondary menu. Add a useful subtitle such as last conversation or next occasion, rather than a percentage bar on every card.

### Put capture at the top of a profile

The mobile profile exposes reminder, edit, and delete controls near the top, but Log is below the brief, health panel, reminders, timeline, family, memory, and plans. The action needed after a conversation is several screens away.

Provide a sticky action row with Message, Log, and Remind. Place edit and delete in an overflow menu. Use a compact identity header and tabs or anchored sections for Overview, Timeline, and Details. Merge the relationship timeline and interaction log into one coherent history with filters and inline editing.

### Replace relationship grades with understandable timing

The health formula labels a contact with a 14-day cadence "Neglected" after eight days, before the agreed interval has passed. An unknown last-contacted date is assigned 100%, making missing information look like excellent relationship health.

Evidence: [health formula and labels](</Users/fernandoamaral/Dev/Personal CRM/lib/utils.ts:22>).

Use neutral states: Not tracking yet, On track, Due soon, and Ready to reconnect. Let the user choose the cadence and pause it. Show "Last spoke 8 days ago; next check-in in 6 days." Relationship closeness should never be inferred solely from elapsed time.

### Make creation progressive

The new-contact form presents roughly twenty fields and places Save at the bottom. On mobile, even the basics fill most of a screen.

Start with name, optional contact method, and a short note. Make Save immediately available. Expand professional details, social links, birthdays, gifts, and custom fields on demand. Let the user add a contact, note, or reminder from the global Add action. Preserve drafts across accidental navigation and interruptions with an explicit privacy-aware draft lifecycle.

### Make the calendar actionable

At mobile size the month grid starts near the bottom of the first screen after the introduction and filter panel. The calendar provides month and agenda views but no direct creation, completion, or rescheduling action on an event.

Default to Agenda on phones, collapse filters into a sheet, and keep the current date plus Add visible. Tapping an empty day should create a reminder or plan. Tapping an event should open the actual source item with Complete, Snooze, or Edit, rather than merely link to the contact. Persist view and filters. Add week/day views only if users need appointment planning; drag-and-drop is lower priority than reliable simple actions.

### Consolidate navigation and terminology

The desktop header wraps labels even at 1280 pixels. Dashboard, Smart Lists, Groups, Reminders, and Calendar overlap conceptually. The app also uses tags as groups in some paths while retaining distinct numeric group tables and routes.

Use Today, People, Calendar, and Settings as the main structure, with a consistent Add action. Saved lists and Circles belong within People; import and connected accounts belong under Settings or onboarding. Choose one user-facing grouping concept and document whether saved lists are dynamic queries or manual collections.

### Give feedback that survives the action

Import feedback is mainly a brief toast. Users need a persistent result summary with counts, duplicate decisions, invalid rows, and retryable failures. Likewise, expose notification-delivery status and sync failures rather than requiring users to infer what happened from the absence of a notification or contact.

Continue the existing work on labels, confirmation dialogs, reduced motion, and contrast. Add manual keyboard, screen-reader, zoom, and real iPhone Safari testing; current automated accessibility journeys target Chromium and do not include the calendar in their primary-route loop.

## Functional and Conceptual Roadmap

### Release 1: Make every promise true

Deliver cloud feature parity, verified recovery, atomic retries and revisions, reliable reminder state, truthful import reporting, time-zone correctness, and updated dependencies. Introduce cloud integration tests with at least two workspaces and test every user-visible action. This is the public-launch gate.

### Release 2: Make the first useful moment fast

Onboarding should ask users to choose a small circle of important people, import only what they want, select a few occasions or cadences, and complete one real follow-up. Do not make importing hundreds of contacts a success metric by itself.

Ship the redesigned Today view, simplified People screen, progressive contact form, sticky profile capture, agenda-first mobile calendar, and a persistent import report. Keep the existing warm palette and readable typography; the highest return is better hierarchy and fewer competing actions.

### Release 3: Deliver reminders users can rely on

Use durable scheduling and delivery records, quiet hours, a workspace time zone, deduplication, snooze, recurrence, and a weekly digest. Offer user-selected push or email delivery and report failures. Test app-closed delivery and duplicate suppression before describing alerts as dependable.

Keep date-only birthdays separate from timed events. Support birthday without known year, optional age display, alert disabled/on-day/advance options, and clear handling of leap birthdays. Children should be linkable to both parents as one person or shared household record, preventing duplicate birthday reminders and divergent details. Support varied family relationships and sensitive lifecycle changes without forcing spouse/child assumptions.

### Release 4: Reduce maintenance

Add one-way contact updates and calendar attendee matching with provenance and user review. Importing data should not silently replace a user's own notes. Use post-meeting prompts to ask whether a conversation happened and capture one note plus a next step.

Finish a shared identity and sync contract before releasing the separate iOS app as a companion. It currently stores a separate local dataset. Choose Cloudflare as the primary service for this product, with an explicit self-hosted support boundary, rather than inheriting the older roadmap's assumption that a self-hosted installation is the universal sync authority.

### Release 5: Add useful intelligence

Start with an evidence-linked brief: last conversation, unfinished commitment, upcoming occasion, and a relevant detail. Then offer structured search such as "friends in Lisbon" or "people I owe a reply to." Optional natural-language search and drafting should show sources and require the user's action to send a message.

A graph is useful when it answers a question: who is connected, who introduced us, or who shares this household. Avoid building a decorative network visualization before those workflows work.

## Architecture Recommendations

- Keep one set of domain rules for dates, recurrence, identity, normalization, idempotency, revisions, and lifecycle transitions. Use SQLite and D1 repositories underneath rather than separate business logic implementations.
- Replace untyped response assumptions and `as never` casts with runtime-validated request and response contracts shared by UI, cloud handlers, and mobile.
- Separate large UI files by user task. The contact profile is nearly 2,000 lines; splitting profile header, capture, history, connections, and data hooks will make behavior easier to test and change.
- Return small directory projections. `SELECT *` includes embedded photos and full notes in list responses; move larger photo assets behind tenant-scoped storage with thumbnails before scaling.
- Process imports, exports, snapshots, and erasure in bounded jobs. Respect D1's query and bind limits; the current bulk API accepts 500 IDs while a single query can bind only 100 parameters.
- Add cloud CI alongside the existing strong local suite: cloud build, migrations, two-workspace API isolation, retry/race tests, backup/restore drill, representative mobile journeys, and capability parity.
- Version and checkpoint the present work. A large portion of the cloud and mobile code is untracked in this checkout; local passing checks do not establish that a deployment is reproducible from a committed revision.

## Product Strategy and Success Measures

The defensible value is low-effort, thoughtful follow-through across personal and selected professional relationships. Family context is useful, but not sufficient differentiation: Monica already emphasizes personal details and relationships, while Dex offers relationship context, integrations, and mobile access. These are current primary-source comparisons, not an exhaustive market study. See [Monica](https://www.monicahq.com/en/) and [Dex](https://getdex.com/).

Avoid competing on the number of CRM features. Validate whether users maintain the habit after the initial import. The scarce resource is willingness to do administrative work about their social life.

Suggested measures, to establish baselines before setting targets:

- Time to first useful reminder or completed follow-up.
- Median time to capture a conversation note.
- Weekly meaningful actions completed, with notification clicks excluded as an outcome.
- Four- and eight-week retention after onboarding.
- Reminder dismissal, snooze, and delivery-failure rates.
- Import reconciliation completeness and successful restore drills.
- Frequency of stale facts, duplicate people, and unresolved sync conflicts.

Use a public explanation of the service, support contact, and accurate privacy/data-hosting information before broader acquisition. The first-run claim that files are processed locally should be rewritten for hosted mode: uploads are processed by the CRM deployment. Do not confuse encrypted downloadable backups with end-to-end encryption of the live cloud database.

## Recommended Decision

Treat Everclose as a promising private beta. Spend the next development cycle on cloud correctness and a simpler daily action loop. Reliable recovery, dependable alerts, fast capture, and a useful Today screen will create more user value than a larger feature inventory or an AI chatbot added to the current foundations.
